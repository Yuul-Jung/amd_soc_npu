SECTION 01

Reset 이후 프로그램 실행

SoC 02에서 mb_reset이 해제되면 MicroBlaze V는 프로그램 실행을 시작한다. CPU는 임의의 C 함수부터 실행하는 것이 아니라 먼저 Reset Vector 주소에서 명령어 Fetch를 시작한다.

Clock 안정 → Reset 해제 → PC ← Reset Vector → Instruction Fetch → Startup Code → main()
Processor System Reset │ │ mb_reset 해제 ▼ MicroBlaze V │ │ PC = Reset Vector ▼ ILMB │ ▼ BRAM │ │ Reset Vector Instruction ▼ Decode / Execute
SECTION 02

Reset Vector와 PC

MicroBlaze V는 Reset 또는 Debug Reset이 발생하면 Pipeline을 비우고 C_BASE_VECTORS + 0x0에서 즉시 명령어 Fetch를 시작한다. 기본 C_BASE_VECTORS 값은 0x00000000이다.

항목기본 기준의미
C_BASE_VECTORS0x00000000Reset 기준 주소
Reset VectorC_BASE_VECTORS + 0x0Reset 해제 후 첫 Fetch 위치
PCReset Vector를 가리킴다음 실행 명령어의 주소
Reset 해제 직후 PC │ └──▶ 0x00000000 │ └──▶ .text.init │ └──▶ Startup Code │ └──▶ main()
Vector Base Address를 변경하지 않은 교육용 기본 구성에서는 Local BRAM이 0x00000000을 포함해야 한다.

SECTION 04

BRAM 주소 범위

SoC 01에서 Local Memory를 16 KB로 설정하고 Base Address가 0x00000000이라면 교육용 기준 주소 범위는 다음과 같이 계산할 수 있다.

16 KB = 16 × 1024 Byte = 16384 Byte = 0x4000 Byte Base Address = 0x00000000 High Address = 0x00000000 + 0x4000 - 1 = 0x00003FFF
항목교육용 기준값
Local Memory Size16 KB
Base Address0x00000000
High Address0x00003FFF
실제 주소는 반드시 Vivado Address Editor와 Vitis Linker Script에서 확인한다. 이 장의 0x00000000 ~ 0x00003FFF는 SoC 01의 16 KB Local Memory를 Base 0으로 배치한 기준 구성이다.
SECTION 05

ELF 프로그램 구조

Vitis에서 C 소스를 Build하면 MicroBlaze V용 ELF(Executable and Linkable Format, 실행·링크 정보를 포함하는 실행 파일)가 생성된다. ELF에는 명령어뿐 아니라 초기값이 있는 변수, 초기화되지 않은 변수, Vector, Stack·Heap 배치 정보가 함께 반영된다.

SECTION 06

Linker Script와 Memory Section

MicroBlaze V의 시작 코드는 생성된 RISC-V BSP와 Linker Script를 사용한다. .text.init의 _boot에서 트랩 벡터·레지스터·스택을 준비한 뒤 C 런타임과 main()으로 연결된다. 설치된 BSP의 실제 시작 심볼과 섹션 배치를 확인한다.

영역내용확인
.text.init / .text시작 코드와 프로그램 명령어Reset 주소에서 실행 가능한 코드 배치
.rodata / .srodata읽기 전용 상수실제 Linker Map의 섹션
.data / .sdata초기값을 갖는 전역·정적 변수초기화 이미지·실행 주소
.bss / .sbss초기화되지 않은 전역·정적 변수C 시작 과정의 0 초기화
Stack / Heap함수 호출·동적 메모리16 KiB BRAM 범위·영역 중복 없음

큰 라이브러리 호출을 추가하기 전에 코드·데이터·스택·힙의 전체 크기를 확인한다. 이 예제는 UART 출력 없이 메모리 변수로 실행을 확인한다.

SECTION 11

BRAM Read / Write 검증 프로그램

실습은 main.c를 Vitis에서 직접 생성하고 아래의 원본 코드를 작성한다. 입력 대조용: main.c 원본 소스.

UART나 GPIO 없이 같은 BRAM 변수에 값을 쓰고, 다시 읽고, 값을 변경해서 다시 쓰고, 변경된 값을 다시 읽는 과정을 Debugger에서 직접 확인한다. 이 코드는 SoC 03의 메모리 동작 확인을 위해 작성한 교육용 예제이다.

BRAM Read / Write 검증 프로그램 · 소스 코드
#include <stdint.h>

volatile uint32_t memory_data  = 0;
volatile uint32_t read_value_1 = 0;
volatile uint32_t read_value_2 = 0;
volatile uint32_t read_value_3 = 0;
volatile uint32_t stage        = 0;

int main(void)
{
    // 1단계: 첫 번째 값을 BRAM에 쓴다.
    memory_data = 0x11111111U;
    stage = 1;

    // 2단계: 방금 쓴 값을 다시 읽는다.
    read_value_1 = memory_data;
    stage = 2;

    // 3단계: 같은 BRAM 변수에 다른 값을 다시 쓴다.
    memory_data = 0x22222222U;
    stage = 3;

    // 4단계: 변경된 값을 다시 읽는다.
    read_value_2 = memory_data;
    stage = 4;

    // 5단계: 두 읽기 값을 더한 결과를 다시 쓴다.
    memory_data = read_value_1 + read_value_2;
    stage = 5;

    // 6단계: 최종 값을 다시 읽는다.
    read_value_3 = memory_data;
    stage = 6;

    while (1) {
        // Debugger에서 값을 확인하기 위한 정지 상태
    }

    return 0;
}
단계동작memory_data읽기 결과
초기초기화0x00000000-
1첫 번째 Write0x11111111-
2첫 번째 Read0x11111111read_value_1 = 0x11111111
3같은 위치에 다시 Write0x22222222-
4변경값 Read0x22222222read_value_2 = 0x22222222
5읽은 두 값의 합을 Write0x33333333-
6최종값 Read0x33333333read_value_3 = 0x33333333
① WRITE CPU ──DLMB──▶ BRAM memory_data ← 0x11111111 ② READ CPU ◀─DLMB── BRAM read_value_1 ← memory_data = 0x11111111 ③ RE-WRITE CPU ──DLMB──▶ BRAM memory_data ← 0x22222222 ④ RE-READ CPU ◀─DLMB── BRAM read_value_2 ← memory_data = 0x22222222 ⑤ CALCULATE + WRITE 0x11111111 + 0x22222222 ↓ 0x33333333 ↓ CPU ──DLMB──▶ BRAM memory_data ← 0x33333333 ⑥ FINAL READ CPU ◀─DLMB── BRAM read_value_3 ← 0x33333333
volatile을 사용하여 Compiler가 이 메모리 접근을 불필요한 연산으로 제거하지 않도록 한다. 변수의 실제 BRAM 주소는 Linker가 결정하므로 특정 BRAM 주소를 코드에 임의로 고정하지 않는다.

SECTION 12

Build와 ELF 생성

Application을 Build하면 MicroBlaze V GNU Toolchain이 C Source를 Compile·Assemble·Link하고 ELF 실행 파일을 만든다.

main.c → riscv64-unknown-elf-gcc → Object → Linker Script → soc03_bram_run.elf
확인 파일의미
*.elfMicroBlaze V 실행 파일
Linker ScriptSection → Memory 배치 규칙
Build LogCompiler/Linker Error, Memory Overflow 확인
16 KB BRAM 범위를 넘어가면 Link 단계에서 Memory Region Overflow가 발생할 수 있다. 이 경우 단순히 BRAM 크기를 키우기 전에 어떤 Section이 커졌는지부터 확인한다.

MicroBlaze V용 RISC-V 컴파일러와 생성 BSP를 사용한다. ELF의 Machine은 RISC-V, ABI는 ILP32이며 ISA 옵션은 CPU에서 활성화한 명령어 확장과 맞아야 한다. 실제 Vitis 2024.2 빌드 로그에서는 -march=rv32i_zicsr_zifencei, -mabi=ilp32를 확인했다. CPU 설정과 빌드 로그를 기준으로 확인한다. 캐시는 ISA 옵션과 별도로 하드웨어 설정에서 확인한다. Build Log의 실제 컴파일러 경로·옵션과 Linker Map을 확인한다.

Application Build 순서 및 ELF 성공 판정

  1. ① 파일 저장

    main.c에서 Ctrl+S. 파일 크기가 0이 아님을 확인한다.

  2. ② Component 선택

    FLOW → Component에 soc03_bram_run 선택. Platform soc_01_platform을 선택한 상태로 혼동하지 않는다.

  3. ③ Build

    FLOW의 Build 클릭 → 하단 OUTPUT의 soc03_bram_run::build 로그 확인.

  4. ④ 성공 로그

    Build Finished successfully와 soc03_bram_run.elf 확인. 실제 로그에서 text 4840, data 204, bss 3532 bytes를 확인했다.

  5. ⑤ 컴파일러 설정

    실제 빌드 명령에서 -march=rv32i_zicsr_zifencei, -mabi=ilp32가 관찰되었다. 임의로 RV32IM이라고 확정하지 않는다.

Linker Script 실제 설정 확인

JTAG 대상은 MDM V에 연결된 MicroBlaze V hart(하트, 실행 하드웨어 단위)를 선택한다. 하드웨어 설정 후 Reset/Halt → ELF 다운로드 → main() 중단점 → Run 순서로 확인한다.

Basys3 연결 및 Ubuntu USB 인식

  1. ① PROG/UART 연결

    Basys3의 PROG/UART USB 단자에 PC의 USB 케이블을 연결하고 보드 전원을 켠다.

  2. ② FTDI 장치 인식

    Ubuntu 터미널에서 lsusb -d 0403:6010 실행. 실제 실습에서는 Digilent FT2232 USB 장치가 확인되었다.

  3. ③ Hardware Server 확인

    ps -ef | grep -E '[h]w_server|[c]s_server' 실행. Vitis가 시작한 hw_server 프로세스가 있는지 확인한다.

  4. ④ JTAG와 UART 구분

    /dev/ttyUSB0이 없어도 JTAG 실패라고 단정하지 않는다. USB 연결 확인과 FPGA JTAG 검출은 별도 단계이다.

  5. ⑤ 다음 단계

    Vivado로 돌아가지 않고 Vitis의 launch.json에서 Bitstream Program을 진행한다. 검색 실패 시 SECTION 19 오류 복구 절차를 적용한다.

최종 FPGA 인식 판정은 Debug 패널에 xc7a35t, RISC-V → Hart #0가 표시되는지로 판단한다.

SECTION 17

Debugger로 Read / Write 확인

이번 실습에서는 volatile 전역 변수와 F10 단계 실행으로 관찰했다. 실제 Build 로그에는 -O2가 보이므로, 정밀한 행 단위 디버깅이 어려운 경우에만 디버그 정보와 -O0 옵션을 설정해 다시 빌드한다. while (1)은 CPU가 반복 명령을 실행하는 대기 루프이며 디버거의 정지 상태가 아니다. 최종값은 Suspend / Halt로 CPU를 멈춘 뒤 Watch에서 확인한다. 각 stage 대입문까지 실행한 다음 아래 표와 비교한다. UG1400 · Debug / Optimization 설정.

Vitis Debugger의 Watch 창에는 memory_data, read_value_1, read_value_2, read_value_3, stage를 등록한다. 각 대입문에 Breakpoint를 걸거나 Step Over로 한 줄씩 실행하면 값의 변화를 직접 확인할 수 있다.

  1. main() Breakpoint

    main() 첫 줄에서 멈춘 뒤 Watch 창에 다섯 변수를 등록한다.

  2. 첫 번째 Write

    memory_data = 0x11111111U; 실행 후 memory_data가 바뀌는지 확인한다.

  3. 첫 번째 Read

    read_value_1 = memory_data; 실행 후 두 값이 모두 0x11111111인지 확인한다.

  4. 덮어쓰기

    memory_data = 0x22222222U; 실행 후 같은 변수 값이 변경되는지 확인한다.

  5. 변경값 Read

    read_value_2가 0x22222222가 되는지 확인한다.

  6. 계산 후 다시 Write

    read_value_1 + read_value_2의 결과인 0x33333333이 memory_data에 저장되는지 확인한다.

  7. 최종 Read

    read_value_3가 0x33333333인지 확인한다.

최종 확인값: stage = 6, memory_data = 0x33333333, read_value_1 = 0x11111111, read_value_2 = 0x22222222, read_value_3 = 0x33333333.

WATCH 변수 5개 등록과 단계별 실행

  1. ① 시작 위치 확인

    왼쪽 DEBUG → RISC-V → Hart #0가 PAUSED ON BREAKPOINT이고 main.c 10행의 실행 표시가 있는지 확인한다.

  2. ② WATCH 등록

    왼쪽 WATCH 제목 오른쪽 + 클릭 후 memory_data, read_value_1, read_value_2, read_value_3, stage를 하나씩 Enter로 등록한다.

  3. ③ F10 / F5 구분

    F10 = Step Over(한 줄씩 실행), F5 = Continue(다음 중단점까지 실행). 단계별 관찰에서는 F10을 사용한다. F5로 전부 실행하지 않는다.

  4. ④ Stage 1 확인

    memory_data = 0x11111111U;와 stage = 1;가 실제로 실행된 뒤 WATCH에서 memory_data=0x11111111, stage=1 확인.

  5. ⑤ Stage 2~5 확인

    각 stage = N;을 실행한 다음 WATCH를 확인한다. 현재 노란 화살표가 가리키는 행은 앞으로 실행할 문장이다.

  6. ⑥ Stage 6 확인

    마지막 stage = 6;을 실행하면 예상값은 memory_data=0x33333333, read_value_1=0x11111111, read_value_2=0x22222222, read_value_3=0x33333333, stage=6.

  7. ⑦ 정지 상태

    while (1)은 CPU가 무한히 실행하는 코드이지 디버거 자동 일시 정지 기능이 아니다. 최종값을 안정적으로 캡처하려면 35행에 중단점을 걸거나 디버거 Pause를 사용한다.

이번 실습에서 WATCH 변수의 단계별 변화는 확인했다. 다만 최종 Stage 6 값이 모두 보이는 스크린샷은 아직 제출되지 않았으므로 아래 표는 C 코드에서 계산되는 예상값으로 구분한다.

실제 오류 ① — JTAG 장치 검색 실패

  1. ① 증상

    Could not find FPGA device on the board for connection 'Local'. 메시지가 나타나며 Debug가 실패했다.

  2. ② USB / 서버 확인

    lsusb -d 0403:6010과 ps -ef | grep -E '[h]w_server|[c]s_server' 명령으로 FTDI USB 장치와 서버를 확인한다.

  3. ③ 드라이버 설치

    cd /tools/Xilinx/Vivado/2024.2/data/xicom/cable_drivers/lin64/install_script/install_drivers 후 sudo ./install_drivers 실행. Driver installation successful. 확인.

  4. ④ 규칙 갱신

    sudo udevadm control --reload-rules와 sudo udevadm trigger 실행. 그리고 물리적으로 Basys3 USB 케이블을 빼고 다시 연결한다.

  5. ⑤ 경고 문구 구분

    드라이버 설치 출력의 CRITICAL WARNING: Cable(s) ... must be unplugged then plugged back in은 안내 문장이지 Bash 명령이 아니다.

  6. ⑥ 재연결 상태

    USB 재연결 후 Bus/Device 번호가 달라질 수 있다. 실제 실습에서는 0403:6010과 USB 권한 crw-rw-rw-를 확인했다. /dev/ttyUSB1만 존재해도 JTAG 연결에는 문제가 없을 수 있다.

  7. ⑦ 정상 판정

    다시 Vitis Debug를 실행하고 xc7a35t → RISC-V → Hart #0가 보이면 연결에 성공한 것이다.

실제 오류 ② — main.c가 0바이트로 비어 있음

  1. ① 현상

    Debug가 main() 중단점에 도착했지만 C 편집기에는 코드가 표시되지 않았다. 확인 결과 main.c 크기가 0바이트였다.

  2. ② 존재와 내용 확인

    ls -lh ~/soc/sw/soc03_bram_run/src/main.c 및 sed -n '1,80p' ~/soc/sw/soc03_bram_run/src/main.c 실행.

  3. ③ 소스 복구

    기존 파일을 백업한 뒤 SECTION 11의 원본 코드를 다시 작성한다. 다른 프로그램으로 대체하거나 변수명 및 1~6단계 구조를 변경하지 않는다.

  4. ④ 재빌드

    wc -c ~/soc/sw/soc03_bram_run/src/main.c의 값이 0이 아닌 것을 확인하고 FLOW → Build를 다시 실행한다.

  5. ⑤ Debug 재검증

    Build Finished successfully. 확인 후 Debug 실행, main.c에 코드가 보이고 10행에서 멈춘 것을 확인한다. 이전 ELF가 남아 있는 것만으로 성공 판정하지 않는다.

SUMMARY

SoC 03 완료 확인

  • Reset 해제 후 MicroBlaze V가 Reset Vector에서 Fetch를 시작한다는 것을 설명할 수 있다.
  • 기본 C_BASE_VECTORS가 0x00000000임을 확인했다.
  • ILMB는 Instruction, DLMB는 Data 접근 경로라는 것을 구분한다.
  • ILMB/DLMB가 Dual-Port BRAM으로 연결되는 실제 구조를 이해한다.
  • 16 KB가 0x4000 Byte임을 계산할 수 있다.
  • ELF의 .text.init, .text, .data, .bss, Heap, Stack 역할을 구분한다.
  • 02장에서 생성한 Bitstream을 포함해 Vivado 하드웨어 설계를 XSA로 내보냈다.
  • XSA를 Export하고 Vitis Platform에 연결했다.
  • Standalone Domain과 MicroBlaze V Application을 생성했다.
  • main.c를 Build하여 ELF를 생성했다.
  • Program Section이 Local BRAM에 배치되는지 확인했다.
  • Basys3 Target과 microblaze_riscv_0 Debug Target을 확인했다.
  • Debugger에서 main()까지 실행되는지 확인했다.
  • Debugger에서 Write → Read → Re-Write → Re-Read 순서를 확인했다.
  • 최종 예상값 stage = 6, memory_data = 0x33333333, read_value_3 = 0x33333333을 WATCH로 확인한다. 실제 최종 캡처로 검증해야 완료이다.
